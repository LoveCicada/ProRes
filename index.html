FFmpeg n9.0.2 · 2026-09-18

六档都能送进片门Alpha 要分两层看

官方源码里，常规 ProRes 的硬解只有两条：macOS 上的 VideoToolbox，以及一块 Vulkan 计算着色器。NVDEC、QSV、VAAPI、AMF、D3D 都没有 ProRes 解码器。

像素格式的请求写在 n9.0.2 源码里。这台 Windows 没有 VideoToolbox，页面不展示硬解画面，也不引用别人的帧率当结果。

01

片门先读帧头，再决定谁来解

软解和硬解共用同一个帧头。alpha_info 是第 17 字节的低 4 位：0 没有 alpha，1 是 8-bit，2 是 16-bit，大于 2 直接判非法。skip_alpha 会把这一位清掉，后面无论软解还是硬解都当成没有透明。

帧头 ap4h alpha_info 可以是 0、1 或 2
软解 prores yuva444p12le 有 alpha 时走 decode_slice_alpha
VideoToolbox · Enable，不强制硬件 ayuv64le 有 alpha 时向 VT 要 16-bit 4:4:4:4
Vulkan 旁注 · 计算着色器，8.1 进入，9.0.2 仍在 dispatch 多 1 个平面 输出是 Vulkan 图像，不是 ayuv64le

ffmpeg -hwaccel videotoolbox -i 输入.mov -f null -
ffmpeg -hwaccel vulkan -i 输入.mov -f null -

第一条只存在于编进 Apple 平台的 FFmpeg。ProRes 用的是 EnableHardwareAcceleratedVideoDecoder，VideoToolbox 可以回落到 Apple 自己的软件解码器。源码还会调用 VTRegisterProfessionalVideoWorkflowVideoDecoders()。

FFmpeg 在软件格式带 alpha 时向 VT 要 ayuv64le（kCVPixelFormatType_4444AYpCbCr16）。这是请求，不是这台机器上看到的画面。

当前在片门里：4444，ap4h。

03

棋盘格还在，才算 alpha 进了像素

第一层在帧头。解析器不管最后谁解码，都会读 alpha_info。规范里会用到它的是 4444 和 4444 XQ。422 的四档正常文件没有这一层数据。

第二层在硬解交出来的表面。VideoToolbox 路径看到软件像素格式带 alpha 标志，就改要 ayuv64le，不再要 p210le 或 p416le。旧的 macOS SDK 如果没有那些 10-bit / 16-bit biplanar 常量，无 alpha 的请求会落到 nv12。

Vulkan 路径把同一个 alpha_info 推进着色器。有 alpha 时多派发一个平面，清图时故意不清 alpha。它解的是 GPU 图像，不经过 AYUV64。

05

片边码

  • proresdec.c：六档 FourCC、alpha_info、软解 alpha、hwaccel 列表。
  • videotoolbox.c：六档都送进 cm_codec_type；ProRes 用 Enable 而不是 Require；带 alpha 时请求 ayuv64le。
  • hwcontext_videotoolbox.c：kCVPixelFormatType_4444AYpCbCr16 映射到 AYUV64。
  • vulkan_prores.c：alpha_info 进入着色器，有 alpha 时多一个平面。
  • Changelog：VideoToolbox ProRes 记在 5.0，Vulkan ProRes 记在 8.1，ProRes RAW 的 VideoToolbox 记在 9.0。
  • configure：ProRes 硬解只有 videotoolbox 与 vulkan 两行，另加 RAW 的两行。
  • FFmpeg HWAccelIntro：VideoToolbox 的解码列表里有 ProRes。

ProRes RAW 是另一个 codec id。n9.0.2 有 prores_raw_videotoolbox，8.0 起就有软解和 prores_raw_vulkan。它走的是拜耳数据，没有 4444 这种 alpha 平面，所以没有放进上面六格。
